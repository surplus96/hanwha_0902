## Phase 3. LLM 오케스트레이션 및 파이프라인 구축

### 3-1. LCEL 파이프 문법

    - 지금까지는 google-genai SDK를 직접 호출했습니다 (client.chats.create(), client.models.generate_content()). 이 방식은 "질문 하나 → 답 하나" 구조에서는 충분하지만, 앞으로 만들 것(RAG: 검색 → 프롬프트 조립 → 생성, 여러 단계가 체인처럼 이어지는 흐름)은 단계가 늘어날수록 직접 짠 코드가 점점 복잡해집니다. LangChain의 LCEL(Runnable/| 파이프 문법) 은 "이 단계 출력 → 저 단계 입력"으로 이어지는 흐름을 표준화된 방식으로 조립하게 해줍니다.

    - 참고: AgentExecutor는 레거시라 배우지 않고, create_agent() 또는 LangGraph StateGraph 기준으로 진행합니다(Phase 6에서 본격 학습). 지금은 LCEL의 가장 기본인 파이프 체이닝만 다룹니다.

### 3-2. 임베딩 모델 선택 · 차원 · 성능 비교

    - RAG를 만들려면(3-4) "질문과 의미적으로 비슷한 문서를 찾는" 임베딩이 핵심입니다. 그런데 임베딩 모델마다 한국어를 얼마나 잘 이해하는지가 천차만별입니다. 이걸 눈으로 직접 확인하지 않고 그냥 "다국어 모델을 쓰세요"라고 배우면 와닿지 않으니, 다국어 모델 vs 영어 전용 모델이 같은 한국어 질의를 어떻게 다르게 처리하는지 직접 비교해봅니다 (체크리스트: "동일 한국어 질의로 검색 품질 차이 확인").

### 3-3. Chunking 전략

    - 실제 문서(예: 100페이지짜리 리포트)를 통째로 임베딩하면 의미가 뭉개집니다 — "이 문서 전체가 무엇에 관한 것인지"는 알 수 있어도, "이 문서의 어느 부분이 질문과 관련 있는지"는 알 수 없습니다. 그래서 문서를 작은 단위(청크)로 쪼갠 뒤 각각 임베딩합니다. 오늘은 4가지 전략 중 Fixed-size(가장 단순)와 Overlapping(문맥 보존, 체크리스트 요구사항)을 직접 구현하며 차이를 비교합니다.

    전략	핵심 아이디어	문제점
    Fixed-size	그냥 N글자마다 자름	문장 중간이 뚝 잘릴 수 있음, 청크 경계에서 문맥 단절
    Overlapping	자르되, 앞 청크의 끝부분을 다음 청크 시작에 중복 포함	경계 부근 문맥이 양쪽 청크에 모두 살아있음

### 3-4. Chroma 벡터DB 적재 + RAG 파이프라인 (검색 → 생성)

    - 3-2(임베딩)와 3-3(청킹)을 합쳐서 실제로 검색이 되는 구조를 먼저 만들고, 그다음에 LLM 생성 단계를 붙였습니다. 한 번에 다 만들면 뭐가 잘못됐을 때 어디가 문제인지 찾기 어려워서, "청킹 → 임베딩 → Chroma 적재 → 검색"까지 먼저 확인한 뒤 생성을 붙이는 순서로 진행.

    - 검색된 문서(Document 리스트)를 프롬프트에 넣을 문자열로 합치는 함수와, `{"context": retriever | format_docs, "question": RunnablePassthrough()}` 형태의 LCEL 조립이 핵심 — 하나의 입력(질문)이 두 갈래로 흘러가서(검색 결과 / 질문 원문) 다시 합쳐져 프롬프트에 채워지는 구조.

    - main.py에 `/rag/query` 엔드포인트로 통합하면서, 기존 하네스(validate_input, check_output_forbidden_words)를 그대로 재사용 — 하네스는 "라우트와 분리된 검증 계층"이라 RAG 쪽에도 그대로 적용 가능.

## Phase 4. 실무형 RAG 시스템 구축 및 최적화

    - Phase 3에서 만든 RAG는 "질문 임베딩 → top-K 검색 → 그대로 프롬프트에 주입"하는 Naive RAG. 실무에서는 이 단계에서 발생하는 구체적 실패 유형(모호한 질문의 낮은 재현율, 키워드 매칭 실패, 문맥 부족)을 진단하고 기법별로 해결.

### 4-1. Advanced RAG 검색 품질 진단

    - 실패를 검색 실패(retrieval failure, 관련 문서를 못 찾음)와 생성 실패(generation failure, 찾았는데 답을 못 만듦)로 구분하는 습관부터 필요. "문맥에 없어서 모른다고 답한 것"은 실패가 아니라 정상 동작이라는 점도 구분 대상 — RAG가 사실 검증 없이 아무거나 답하지 않았다는 증거.

    - 진짜 검색 실패는 동의어/다른 표현("심층학습" vs "딥러닝")처럼 의미는 같은데 단어가 달라 임베딩 유사도가 낮게 나오는 경우 재현되기 쉬움.

### 4-2. Multi-Query Retriever

    - 질문 하나를 LLM이 여러 버전으로 재작성해서 각각 검색한 뒤 결과를 합침. "심층학습이 뭐야?"처럼 원본 문서엔 "딥러닝"이라고만 적힌 경우, 기본 retriever는 놓치지만 재작성된 질문("딥러닝이란?") 덕분에 찾아냄.

    - 비용 트레이드오프: 질문 재작성 자체가 LLM 호출 1회 추가. 요청 1건당 API 호출이 늘어나므로 무료/저비용 한도가 있는 환경에서는 체감이 큼.

### 4-3. 하이브리드 검색 (Dense + Sparse)

    - Dense(임베딩 기반 의미 검색)는 고유명사·정확한 키워드(제품명, 오류코드, 버전번호)에 약함 — 의미는 비슷한데 실제로 필요한 정확한 문자열은 놓칠 수 있음. Sparse(BM25, 키워드 검색)로 이 약점을 보완.

    - EnsembleRetriever로 Dense와 BM25 결과를 가중치(0.5:0.5)로 합침. BM25는 순수 통계 기반이라 API 호출이 전혀 필요 없음 — 비용 부담 없이 실습 가능.

    - 제조 설비 매뉴얼처럼 모델명·오류코드(E-108, E-204 등)가 많은 도메인에서 효과가 뚜렷하게 재현됨 — 정확한 오류코드 질의에 대해 하이브리드 적용 전/후로 검색 정확도 차이를 직접 확인.

### 4-4. Parent Document Retriever

    - 작은 단위(child, 문장 수준)로 정밀하게 검색하되, 실제 생성에는 그 문장을 포함하는 더 큰 부모 문서(parent)를 통째로 넘기는 기법. "검색 단위"와 "생성에 필요한 문맥 단위"가 다르다는 문제 해결.

    - vectorstore(child 임베딩)와 docstore(parent 원문)를 분리해서 관리 — child_splitter만 지정하고 parent_splitter를 안 주면, add_documents()에 넣은 원본 문서 전체가 그대로 parent가 됨.

    - 기존 하이브리드(Dense+BM25) 파이프라인과는 인덱싱 구조 자체가 달라(BM25는 작은 조각 반환, Parent Retriever는 큰 문서 반환) 하나의 결과 리스트로 합치면 일관성이 깨짐 — 개념 검증용 독립 스크립트로 확인하고, 실제 병합은 보류.

### 4-5. Self-RAG

    - 검색 필요 여부 / 검색 결과의 관련성 / 생성한 답변의 근거 충분성, 이 세 가지를 모델 스스로 판단하게 만드는 반성(reflection) 개념. 세 번째("근거 충분성")는 이미 Faithfulness judge로 구현되어 있었으므로, 새로 만든 건 첫 번째("검색이 필요한가?") 라우팅.

    - should_retrieve(): 질문을 보고 검색이 필요한지 판정 → 불필요("안녕", "너는 누구야?" 같은 잡담)하면 RAG 파이프라인 자체를 생략하고 바로 일반 대화로 처리. 판정 자체가 실패하면 안전하게 "검색 필요"로 fail-open.

    - 실측 효과: 검색이 필요한 질문은 API 호출 4회(재작성+생성+judge 등) 그대로, "안녕" 같은 질문은 2회(라우팅 판정+직접 답변)로 절반 감소 — 정확성뿐 아니라 비용/지연시간도 개선.

### 4-6. RAGAS 정량 평가

    - 골든 데이터셋(질문+정답 6개 쌍)을 만들고, 실제 서비스와 동일한 RAG 파이프라인(answer_with_context())으로 답변을 생성한 뒤, RAGAS 라이브러리로 4대 지표를 채점.

    - 지표	의미
      Faithfulness	생성된 답변이 검색된 근거에서 실제로 뒷받침되는가
      Answer Relevancy	답변이 질문에 실제로 부합하는가
      Context Precision	검색된 청크들이 실제로 관련 있는가
      Context Recall	정답에 필요한 정보가 검색된 문맥에 실제로 포함되어 있는가

    - 결과: Faithfulness 1.000 / Answer Relevancy 0.885 / Context Precision 1.000 / Context Recall 1.000. Answer Relevancy만 100%가 아닌 건, 답변이 질문을 단답형으로 되풀이하지 않고 친절하게 풀어서 설명하는 스타일이라 순수 임베딩 유사도가 약간 낮게 나온 것 — 결함이라기보다 답변 스타일의 트레이드오프.

## project_exercise — OpenAI 포팅 및 실무 강화

    - project_edu(Gemini 기반)를 그대로 복제해서 OPENAI_API_KEY를 쓰는 버전으로 전환. 이후 실습은 이 프로젝트를 기준으로 계속 진행.

### 포팅 — Gemini SDK → OpenAI SDK

    - 가장 큰 구조적 차이: google-genai는 client.chats.create()로 상태를 가진 채팅 세션 객체가 히스토리를 자동 관리하지만, OpenAI Chat Completions API는 완전 무상태(stateless) — 매 호출마다 messages 리스트 전체를 직접 넘겨야 함. chat_sessions에 {"model":..., "messages":[...]}를 직접 관리하는 구조로 새로 작성.

    - 구조화 출력(judge)도 response_schema → client.chat.completions.parse(response_format=PydanticModel)로 교체, 결과를 message.parsed로 즉시 수령.

    - 포팅 중 발견한 버그 2개: (1) API 호출 실패 시 직전에 추가한 사용자 메시지가 히스토리에 그대로 남는 문제 → 실패 시 pop()으로 롤백. (2) OpenAI 구조화 출력은 거부 시 예외 대신 message.refusal로 알려주는데, 이걸 처리 안 하면 기존 재시도/fail-open 로직을 타지도 못하고 죽음 → refusal이 있으면 명시적으로 예외를 발생시켜 기존 로직에 흡수되게 수정.

### 가드레일 — 실무 표준 카테고리로 강화

    - 리서치 기반(OpenAI Moderation, Llama Guard, AEGIS 2.0)으로 judge의 안전성 규칙에 증오·괴롭힘 / 폭력 / 성적 콘텐츠(미성년자 포함 시 무조건 위반) / 자해·자살 / 불법행위 5개 카테고리를 명시적으로 추가. 같은 카테고리를 시스템 프롬프트의 금지사항 섹션에도 반영해 계층 방어(defense in depth) 구조로.

    - PII 체크는 단어 목록 대신 정규식 패턴(주민번호/카드번호/전화번호 형식)으로 — 단어 매칭은 의미 판단이 필요한 카테고리(증오/폭력 등)엔 무력하고, 형식이 고정된 PII에만 적합하다는 것을 구분해서 이해.

### RAG 재구성 — 검색 중복 버그 발견 및 수정

    - main.py의 /rag/query가 get_context()와 answer_question()을 각각 따로 호출하는 구조였는데, 둘 다 내부적으로 같은 MultiQueryRetriever를 독립적으로 재실행 — 요청 1건에 질문 재작성이 2번(서로 다른 결과로) 일어나는 낭비이자, Faithfulness judge가 실제 생성에 쓰인 문맥과 다른 문맥을 채점할 수 있는 신뢰성 결함이었음.

    - answer_with_context() 하나로 통합: 검색을 1회만 수행하고 그 결과를 생성과 채점 양쪽에 동일하게 재사용하도록 rag_service.py 재구성.

### LangSmith 관측성 도입

    - LangSmith는 LCEL 체인/에이전트 실행을 트리 구조로 자동 기록하는 트레이싱+평가 플랫폼. 지금까지는 logging 모듈로 텍스트 로그를 손으로 대조해가며 디버깅했는데(검색 중복 버그도 그렇게 찾음), 트레이스 트리를 보면 훨씬 빠르게 잡을 수 있다는 걸 실제로 검증.

    - wrap_openai(client, tracing_extra={"client": langsmith_client})로 raw OpenAI 호출(judge, /chat)을, @traceable(name=...)로 라우트 함수 자체를 감싸서 요청 1건 = 트레이스 트리 1개로 통합. LCEL 체인(RAG)은 환경변수만으로 자동 추적되지만, 라우트 함수 밖(예: 스트리밍 제너레이터)에서 실행되는 부분은 자동으로 안 묶여서 get_current_run_tree()로 수동 연결이 필요한 경우도 있음 — 완벽하게 하려는 시도는 복잡도 대비 실익이 낮아 기존 상태로 유지.

    - 데이터 거버넌스: harness.PII_PATTERNS(정규식)를 그대로 재사용해 create_anonymizer를 만들고 LangSmith Client에 연결 — 트레이스가 제3자 서버로 나가기 직전에 PII를 마스킹. 같은 정규식 자산으로 "응답 보호"와 "트레이스 보호" 양쪽을 다 방어하는 구조.

    - 비용 관련 사실 확인: LangSmith 무료 티어(월 5,000 트레이스)는 멀티 에이전트라고 특별히 막히지 않음 — 트레이스 "양"에 비례해 과금. 실제로 유료가 필요해지는 건 LangGraph Platform(관리형 배포/호스팅)이지, 우리처럼 자체 서버에서 직접 실행+트레이싱하는 방식은 무료 범위로 충분.
